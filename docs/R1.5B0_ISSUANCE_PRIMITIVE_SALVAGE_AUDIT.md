## E. PDF renderer determinism

### Mechanism (read from source)

- Engine: `pdfmake@0.2.20` → `@foliojs-fork/pdfkit@0.15.3` (pinned by `package-lock.json`; `package.json` uses `^`).
- `info.creationDate = new Date(model.issuedAt)` overrides pdfkit's `CreationDate: new Date()` default.
- `ModDate` is written only when supplied: it is **absent**.
- Trailer `/ID` = `MD5(CreationDate.getTime() + every info key/value)` (`PDFSecurity.generateFileID`), so it is a pure function of the info dictionary. **No random identifier.**
- Fonts: the standard-14 `Helvetica`/`Helvetica-Bold` AFM metrics bundled in pdfkit. Nothing is embedded and nothing is read from the OS, so there is no font substitution at render time.
- Images: one PNG (`logo-on-light.png`) read with `readFileSync` on every render. If the asset ID is registered but the file is missing, the render throws, so there is no silent fallback. The path resolves module-relative first and falls back to `process.cwd()`.
- No network access, no `Date.now()` in the definition, no locale-dependent formatting: all display strings are pre-formatted with explicit code (`formatClpMoney`, UTC getters).

### Experiment (isolated, read-only)

The existing fixtures (`src/scripts/pdf-fixture.ts`) were rendered as 1, 10 and 100 lines, with:
a fresh renderer per call, one shared renderer, 8 concurrent renders on the shared renderer,
three separate processes (`TZ=UTC`/`LANG=C`; local `America/Santiago`, UTC−3/`es_CL.UTF-8`; local),
then in one process `process.env.TZ` switched among `UTC`, `Asia/Tokyo`, `America/Los_Angeles` and `Pacific/Kiritimati`.

| Fixture | SHA-256 (all runs) |
|---|---|
| 1 line | `1440709da616fd663970a03e8b840df9bd8799888b487a2309fa91457cf8efc4` |
| 10 lines | `2d5a5666b7f96d14a66a4ffc1c5248f071bb0051a9a26f73cf0d92744236d7f6` |
| 100 lines | `4410d7d6af0bb7dd5860f8b1ddfadd669988398856f14d42e682ff6e26cc747f` |

Every condition produced exactly one hash per fixture. Two controls confirmed the
hash is sensitive to its inputs: changing `quoteNumber` changed the hash, and
changing only `issuedAt` by 1 s changed it too (through `CreationDate`/`/ID`).
Info dict observed: `/CreationDate (D:20260909120000Z)`, no `/ModDate`,
`/ID [<f768e3ae…> <f768e3ae…>]`, `%PDF-1.3`, 6 933 bytes.

### Verdict

**PROVEN** for a pinned build (same lockfile, same Node major, here Node 22.23 on
Windows), independent of process, time, timezone, locale, renderer reuse and
concurrency.
**LIKELY** across OS (Linux container): there is no platform-dependent input, and
content streams are deflated by the zlib bundled with Node. This was not measured
on Linux.
**NOT GUARANTEED** across a pdfmake/pdfkit upgrade or a Node upgrade that changes
zlib output.

### Is determinism required for V2 safety?

**No, for issuance correctness.** The contract (§9.3, Idempotency §4.6) and the
schema make the first committed manifest win:

- Different retry bytes give a different SHA, which means a different content
  address. Two attempts never write to the same path with different bytes.
- The fenced commit lets exactly one generation insert the manifest, and
  `quote_documents_quote_unique` allows only one manifest per quote.
- The losing attempt's file is an unreferenced, complete, immutable
  orphan. It is harmless.

**Yes, for two secondary properties:**

1. **Operator repair** (§9.3: re-render "MUST reproduce the recorded
   `pdfSha256`"). This works only if `(snapshot, rendererVersion, templateVersion)`
   reproduces bytes long after issuance. That makes the dependency lockfile, Node
   major and asset bytes part of the `rendererVersion` contract: a renderer
   dependency bump must bump `rendererVersion`, and repair must run the matching
   build.
2. **Orphan minimization.** With determinism, a reclaim after a crash in "after
   write, before commit" finds and reuses the same address.

Two current threats to determinism must be removed in B2. Neither shows up in the
experiment, because the fixture and environment were fixed:

- `QUOTE_RENDER_VERSION` is an **env value**. `.env.example` already says
  `quote-pdf-v2-pdfmake` while the code default is `quote-pdf-v3`, so the
  manifest label can lie about the bytes. The fix is a code constant.
- Issuer legal name (`QUOTE_COMPANY_NAME`) and the logo file are **live
  configuration**: changing either changes the bytes under the same version label.
  The fix is to pin both in the issuer profile/template version and load assets
  once at construction.

## G. Filesystem storage findings

Target (Domain §9.4): `<root>/artifacts/sha256/<aa>/<bb>/<sha>.pdf`, temp file → fsync → atomic rename → re-read verify. The DB check `quote_documents_content_addressed` already pins the exact key format.

| Capability | Today | Note |
|---|---|---|
| Content-addressed keys | No key builder (V1 `document-paths.ts` deleted) | New pure `contentAddressedPdfKey(sha)` identical to the DB check |
| Write-once | **No**: `writeFile` (flag `w`) truncates and overwrites | |
| Atomic publication | **No** | |
| Temp + rename | **No** | |
| Same-hash existing-file verification | **No** (`exists()` only checks presence) | |
| Silent overwrite prevention | **No** | |
| Path traversal protection | **Yes**: charset regex, `..` rejection, resolved-path prefix check (also catches a leading `/`) | Symlinks inside the root are followed (no `realpath`). Low risk on a service-owned volume |
| Parent directory creation | Yes (`mkdir -p`) | |
| Concurrent writers | Unsafe (see below) | |
| Crash during write | Leaves a **truncated file at the final key** | |
| Partial file detection | None at write time; the verifier detects later | |
| fsync / durability | None (file or directory) | |
| Read by key | Yes (`readBuffer`, `createReadStream`) | Stream is unverified. The endpoint must verify first (§9.3) |
| Byte hashing | Hash of the **input buffer**, not the re-read bytes | |
| Health probe | Yes: write/read-back/delete in `.health/`, stale-probe sweep after 60 s, failure classification | KEEP |
| Temp cleanup | Only for probe files | The pattern can be reused for issuance temp files |
| Immutability policy | None in storage. `deletePrefix`/`deleteStorageKey` are public | Must not be reachable from V2 issuance |

**Worker A and B render the same quote concurrently.** The protocol should make
this impossible: only one generation holds the lease. It is still reachable with
a zombie (A's lease expired, B reclaimed).

- Deterministic bytes, same SHA, same path, current code: two in-place truncating
  writes race. The final content ends up correct because the bytes are identical,
  but a reader in between (B's verify step, the document endpoint) can see a
  truncated file. If A crashes mid-write after B verified, B's committed manifest
  points at a truncated file. **I6 is violated.**
- Different bytes: different paths, no interference. A's file becomes an orphan.

**Crash after the bytes are written, before the manifest commit.** Current code
leaves a complete file at the final key, or a partial one if the crash was
mid-write. A retry that reuses by `exists()` would accept the partial file.

**Required publish primitive (B3):**

1. `bytes → sha`
2. `open('<root>/artifacts/tmp/<sha>.<uuid>.tmp', 'wx')`, write, `fsync(fd)`, close
3. `mkdir -p` the target dir, then `link(tmp, final)`, which is atomic and
   **fails with `EEXIST` instead of overwriting**
4. On `EEXIST`, read the existing file and hash it: if it matches, reuse; if not,
   raise `document_storage_failed` and an operator incident. Never replace.
5. `unlink(tmp)`, then `fsync` the target directory (Linux; skip where unsupported)
6. Re-read the final file and verify the SHA (contract step 4)

`tmp/` must be on the same filesystem as `artifacts/`. Use a fixed subdirectory of
the root.

`rename` is acceptable as a fallback (atomic, but it replaces), because a verified
same-hash file holds identical bytes. `link` gives true write-once.

**Decision: REFACTOR.** Keep the class's root/key/probe/read core and add the
publish primitive. Do not expose deletion to issuance. A separate wrapper
interface (`ContentAddressedArtifactStore { publish, readVerified }`) is the V2
surface.

## H. DB ↔ filesystem crash-window analysis

There is no distributed transaction. The governing rule: **a recoverable orphan
file is acceptable; a manifest without bytes is not.**

### A. render → write artifact → fenced DB manifest commit (contract §4.3)

| Crash point | Durable DB | Durable FS | Retry safe? | Orphan? | Cleanup |
|---|---|---|---|---|---|
| During render | op `running` (gen g), quote `issuing` | nothing, or a temp file | Yes: lease expiry, then claim g+1 | temp only | age-based temp sweep |
| During temp write/fsync | same | partial **temp** | Yes | temp only | temp sweep |
| After link, before commit | same | complete content-addressed file | Yes: reclaim re-renders; same SHA → `EEXIST` → verify → reuse; different SHA → second file | possibly one (non-deterministic case) | none required (harmless, immutable) |
| Commit sent, outcome unknown (`CommitOutcomeUnknownError`) | committed or not | complete file | Yes: re-read the op; if `succeeded` done; else lease expiry and retry (fenced) | maybe | none |
| After commit | op `succeeded`, manifest, quote `issued` | complete file | n/a | no | none |
| Zombie commit after reclaim | `generation` changed, so 0 rows: abandon | its file | n/a | possibly | none |

The bytes always exist before any manifest names them, so I5 and I6 hold. Residue
is limited to temp files and unreferenced immutable artifacts.

This is the only sequence the current primitives support once the storage publish
primitive exists. It needs no new tables and no schema change.

### B. render → DB reservation → write → DB finalize

A reservation row (or a manifest in a pending state) would need a schema change:
`quote_documents` is insert-once and immutable (guard trigger) with no state
column. It adds a crash window where the DB names a reserved artifact that does
not exist, and so a second reconciliation path. **Rejected:** it adds a state
without removing a risk, because the fencing generation already serializes
writers.

### C. temp artifact → DB transaction → publish/finalize

This commits the manifest before the bytes are at their address. A crash between
commit and rename leaves `issued` with a manifest whose `storage_key` does not
exist: **I5/I6 are violated**, the exact failure the rule forbids. **Rejected.**

**Conclusion: sequence A**, exactly as Idempotency §4.3 specifies.

## I. Hashing and snapshot identity

| Hash | Algorithm | Function | Trust |
|---|---|---|---|
| Request fingerprint | `SHA-256(JCS({operation, pathParameters, body}))` | `sha256Jcs` via `commandContext` | Trusted (R1.5A, tested) |
| **Semantic snapshot hash** (`issuance_operations.snapshot_hash`, `quote_documents.semantic_snapshot_hash`, algorithm `jcs-sha256-v2`) | `SHA-256(JCS({quoteId, quoteNumber, currency, issuerProfileId, issuedAt, validity, customer, lines, shipping, totals}))` | `semanticSnapshotHash(quoteView)` in `quote-v2-acceptance.ts` | Algorithm trusted. **Input coupling is a risk**: the lines/shipping/validity members are the `readQuote` read-projection objects. A future harmless-looking change to `lineView` changes the hash of every existing `issuing` quote, so the worker's pre-render integrity check would refuse it |
| **PDF byte hash** (`pdf_sha256`) | SHA-256 of the bytes | inline `crypto.createHash` in storage/verifier | Trusted, but in storage it is computed from the input buffer, not the re-read bytes |
| Storage key | `artifacts/sha256/<aa>/<bb>/<sha>.pdf` | **none in code**; only the DB check constraint | Must be built |
| V1 content hash | `toCanonicalJson` (non-JCS) | `createIssuedQuoteContentHash` | Legacy only. Legacy manifests record it and are never recomputed. **Not for V2** |

Semantic snapshot hash ≠ PDF hash. The first identifies **what must be rendered**
and is fixed at acceptance. The second identifies **what was rendered** and is fixed
at commit. The worker must load the snapshot from the DB, recompute the semantic
hash, compare it to `operation.snapshot_hash`, and fail (no render) on mismatch.
That makes I7 checkable.

## J. Periodic runner findings

| Property | Finding |
|---|---|
| Scheduling | `setTimeout` chained **after** each iteration completes (fixed delay, not fixed rate). No drift accumulation, no overlap |
| First run | **Delayed** by `intervalMs` after `start()` |
| Overlap / concurrent invocation | Impossible within a process: `runNow()` joins an in-flight run |
| Single-process | Yes. No cross-process coordination, and none needed: the DB claim is the coordinator |
| Shutdown | `stop()` clears the timer and awaits the in-flight iteration (unbounded here, bounded by `APP_SHUTDOWN_TIMEOUT_MS` at app level) |
| Readiness | `canRun()` gate. Skipped iterations are not failures; one `job.paused` / `job.resumed` log per outage |
| Exceptions | Caught; logs `errorName`/`errorCode` only (no driver message, so no PII). Process survives |
| Retry/backoff | None (fixed interval). Correct for a trigger |
| Clock | `new Date()` only for status timestamps. No scheduling decision depends on wall time |
| Testability | `runNow()` drives it deterministically (existing tests) |
| Timer | `unref()`'d: never keeps the process alive |

**Can it be only a trigger for "attempt to claim durable work"? Yes, and that is
the correct role.** All reliability (claim, lease, fencing, backoff, deadline) lives
in SQL on `issuance_operations`. Losing a tick, a restart, or two instances ticking
at once changes nothing durable. **WRAP**, with three wiring rules for B1:

1. **Gate granularity.** `canRun = monitor.isReady()` pauses the job whenever
   storage or the renderer is down. For attempts that is correct (I15). For the
   **deadline sweep** it is wrong: the sweep is DB-only, and pausing it during a
   storage outage would leave operations `pending` past `deadline_at` until storage
   returns, delaying T6. Run the sweep as its own runner gated on database
   readiness only, or branch inside `execute`.
2. **No abort signal.** `execute` must check `lifecycleState.isShuttingDown`
   before each claim and process a bounded number of operations per tick, so
   `stop()` returns quickly.
3. **Lease renewal is not a periodic job.** It is a per-attempt timer
   (`lease/3`) with a fenced `UPDATE … WHERE generation = :g`. Use a small helper,
   not this runner.

## M. Orphan cleanup findings (historical)

- **What counted as orphaned:** any file under `quotes/` whose key was not among
  the keys of currently *issued* quotes (`listIssuedDocumentArtifacts`) and whose
  `mtime` was older than `QUOTE_DOCUMENT_ORPHAN_MIN_AGE_MS` (default 5 min).
  `QuoteDocumentAccessService.cleanupOrphanedArtifacts` had **no age guard at all**.
- **How it identified files:** directory listing and the V1 key layout (rebuilt
  email-HTML key).
- **Race safety:** none. It read the referenced set and the listing at different
  times, without locks, and knew nothing about in-flight attempts. An attempt that
  stalled for longer than the minimum age between write and commit (DB outage,
  GC pause, slow commit) lost its file, then committed a manifest pointing at
  nothing.
- **V2 specifics that make it worse:** with content addressing, an orphan *today*
  can be **adopted** by a later retry ("`EEXIST` → verify → reuse"). A sweeper
  that deletes it between the retry's verify and its commit violates I6.

**Decision:** DELETE both the code and the concept as implemented. For R1.5B:
**never delete content-addressed artifacts.** The contract says nothing is deleted
until a retention policy is ratified (U1), and orphans are harmless. Sweep only
issuance **temp** files by age, reusing the stale-probe sweep pattern. A future
orphan policy (post-U1) must exclude every hash referenced by a manifest *or*
producible by an active operation, and should quarantine rather than delete.

## N. Security and resource findings

### Security

| Area | Finding |
|---|---|
| Path traversal / arbitrary read-write | Storage keys are validated and confined to the root (regex, `..`, resolved-prefix check). The V2 key is derived from a hex SHA, never from caller input. Symlinks are not resolved (low) |
| HTML injection | PDF: pdfmake text nodes are not markup; `<script>…` rendered as literal text. Email HTML (R1.6) relies on `escapeHtml` |
| pdfmake injection surface | `image`, `svg` and `link` properties can read local files or embed URLs. **Rule for B2:** snapshot data may appear only in `text` nodes, never in `image`/`svg`/`link`/`font` fields |
| Network during render | None (verified: no `http(s)://` in output; no remote resources) |
| Filesystem path leakage | Node `fs` errors carry absolute paths in `message`. The runner already logs only name/code. The worker must store only the contract error code in `last_error_code` and log code-only |
| Browser/subprocess argument injection | N/A (no browser, no subprocess) |
| Sensitive logging | Renderer errors may echo text. Never log snapshot content. The audit trail holds codes and hashes |
| Capability URLs | V1 HMAC `doc_` refs removed. V2 document access is principal-authenticated (R1.5B4) |
| Personal data on the document | The default signature names an employee with phone and address. This is a V1 artifact. Replace it with the issuer profile (U3) |

### Resources

- No Chromium startup cost. pdfmake is in-process; documented benchmark
  ~50–115 ms and +5–25 MB RSS per concurrent render; 10 concurrent ≈ +50 MB.
- Layout is **synchronous CPU on the event loop**: it cannot be cancelled or timed
  out preemptively. The contract caps the input (≤ 100 lines, bounded text), so
  the worst-case PDF is ~32 KB and ~100 ms. Keep **one attempt at a time per
  process**, with a per-attempt budget well below `issuanceLeaseMs` (60 s). A hung
  attempt is then recovered by lease expiry.
- `readFileSync` of the logo on every render: synchronous I/O on the event loop
  and a determinism hazard. Load once at construction.
- Temp-file accumulation: bounded by the age sweep (B3).
- Runaway workers: bounded by fixed-delay ticks, no overlap, a per-tick claim cap,
  `generation`/`attempt_count` monotonicity and `deadline_at`.

## R. Recommended slicing

The proposed shape holds with one change, based on the evidence. The renderer/V2
document-model refactor is the largest and most content-sensitive piece (U2, U3,
font). It is pure and DB-independent, so it gets its own slice. Artifact
publication and the manifest commit move together into the slice that owns the
DB↔FS atomicity boundary. Retry, reclaim and deadline cannot be a later slice:
reclaim is the same SQL statement as claim, and fail-with-backoff is the only
non-success exit of an attempt. They belong in B1.

### R1.5B1 — Durable operation core (DB-only)

- **Responsibility:** operation repository (claim incl. expired-lease reclaim, fenced renew, fenced fail-with-backoff, deadline sweep, T10 operator-retry state primitive); worker loop skeleton with an injectable *attempt body*; instance id; issuance config; runner wiring (attempt runner gated on full readiness, sweep gated on DB only); shutdown checks; shared issued-snapshot loader + semantic-hash recheck.
- **Reuses:** `PeriodicJobRunner`, `BackgroundJobManager`, `ApplicationLifecycleState`, `DependencyMonitor`, `withTransaction`/`CommitOutcomeUnknownError`, `appendAudit`, `readQuote`/`readOperation`, `sha256Jcs`/`semanticSnapshotHash`.
- **Replaces:** hard-coded `ISSUANCE_DEADLINE`; the email retry schedule is not reused.
- **Closure gate:** integration tests on real PostgreSQL: N concurrent claimers → one holder; zombie renew/fail → 0 rows; lease expiry → reclaim with gen + 1; backoff schedule and deadline cap; sweep fails `pending` and `running`-expired ops but never a live lease; quote stays `issuing` (I11/I12); T10 creates a new op and respects one-active; the sweep runs while storage is "down"; shutdown stops claiming. The attempt body is a test double that can only fail (no success path yet).

### R1.5B2 — V2 document model, renderer and template v4 (pure)
