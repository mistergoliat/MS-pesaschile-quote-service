## H. Pending snapshot and recovery behavior

The current release retains the archived v4 text and unchanged renderer/assets,
so a pending v1 snapshot can finish only using that preserved v1/v4 combination.
Retry/reclaim/operator retry loads the frozen id; it never selects v2 through the
acceptance constant. Unknown profiles fail closed.

A disposable integration fixture represents a pre-release v1 acceptance. It
checks the frozen hash and identity before/after operator retry, lets the real
worker finish, and compares actual bytes with its archived v1/v4 rendering.
The committed manifest stays v4, with the original snapshot hash and v1 issuer.
The fixture setup is explicitly test-only; no existing production state is changed.

Repair keeps the existing exact-current-version policy. An intact v4 artifact is
left untouched; a missing v4 artifact is refused with `TEMPLATE_VERSION_MISMATCH`
by the current v5 repair tool, with no publication or table changes. Restore exact
backed-up bytes, or use the archived base image/code and matching pinned assets
for old-manifest repair. Current v5 repair reproduces only its exact recorded
hash/length. Never relabel a v4 manifest as v5 or replace an old snapshot with v2.

This is supported archived-template behavior, not a general compatibility
dispatcher or a claim that arbitrary past/future renderer versions are repairable.
No production pending-operation inventory or archive deployment was performed.
