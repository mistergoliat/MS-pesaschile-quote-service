## H. Secret-management requirements and observed security gaps

The expected **generic** source is the deployment/host secret store (Security §6, `principals.md`, bootstrap prerequisites). **No concrete store, deployment wiring, ACL, rotation owner or recovery implementation is selected in-repo**: F05 blocks production preparation sign-off. Do not say secrets are absent in production; production was not inspected.

Required design: inject runtime DB and optional Gmail credentials only into the runtime process; migration credentials only into the maintenance process; registry hashes mounted read-only from the selected store; raw caller tokens reside in each caller's store. Prefer the file registry for live rotation. No secrets in Git, image layers/build args, shell history, command arguments, logs, health, audit, ordinary operator output or backup bundles. Constrain host/service/backup-reader access and recover secret references through the store's own audited recovery process.

Repository positives: only `.env.example` is tracked among `.env*`; `.env` and `var/` are ignored; Docker excludes `.env*`/`var` and explicitly copies source/build inputs; health output omits credentials/DSNs/paths; Gmail adapter never logs provider bodies or tokens; HTTP error/operator shells sanitize normal failures; R1.6D hostile redaction tests cover request/job/Gmail and verifier surfaces. This is not a scan of all Git history or proof of external secret-store controls.

Two concrete code gaps require bounded security fixes, not commercial changes:

- **F06:** `src/server.ts:errorSummary` returns arbitrary `error.message` and `error.stack` into init/bind/fatal logging and direct stderr. Header redaction does not sanitize these free-text fields. `src/scripts/migrate.ts` also prints arbitrary `errorMessage` from the driver/runner. Secret/PII/path exclusion is therefore not guaranteed for these paths. Existing log-redaction tests exercise an HTTP error and `documents:verify`, not all process-fatal/migration failures. Preserve useful ids/codes for migration exceptions while preventing arbitrary provider/driver values from entering output; add hostile local error coverage in the authorized fix slice. No actual secret leak was claimed or sampled here.
- **F07:** `postgres.ts:buildConnectionConfig` sets `{rejectUnauthorized:false}` when mode is `require`. It encrypts but does not authenticate the DB server. Migration/check/grant/verify use connection-string-only `pg.Client` configuration; `DATABASE_SSL_MODE` does not configure those paths. Select same-host loopback DB or authenticated TLS between hosts, and demonstrate consistent runtime/operator/maintenance behavior. Do not claim `require` proves secure production TLS, or assume an unimplemented CA variable exists.

`principals:token` deliberately prints a newly generated raw token once; it is a provisioning tool, not routine sanitized operator output. Execute only in an explicitly authorized secure provisioning channel, deliver to the caller's store, and exclude capture from operational logs/backups. It was not run here.

## K. Storage assumptions

Evidence: `content-addressed-artifact-store.ts`, artifact port, Domain §9.4, Dockerfile; production durability is unverified (F11).

Production target of the adapter is a persistent **single-host Linux filesystem**, mounted at the configured root (image default `/var/lib/pesaschile/quote-documents`). The image uses non-root `nodeapp`; the actual mounted volume must match its deployed UID/GID, restrict other writers/readers, and stay available through image replacement/host recovery. Docker `VOLUME` alone does not choose, protect or back up a production volume.

Layout: `artifacts/tmp/<sha>.<uuid>.tmp` and `artifacts/sha256/<aa>/<bb>/<sha>.pdf`. Temp is exclusive `wx`, fully written and fsynced, then **hard-linked** atomically to the final path. EEXIST is verified/reused only for identical hash/length; differing bytes cause `integrity_conflict`. Final directory/parent are fsynced on POSIX and final bytes reread. This is a concrete no-overwrite implementation of the frozen atomic-publication intent, not an overwriting rename.

Temp and final must be on the **same filesystem** with supported hard links, fsync and durable directory entries; no nested mount splitting them. Do not assume object storage/NFS/multi-host copies satisfy this protocol. Readiness probes hard links in tmp, but does not prove backup durability, volume identity, all final-directory permissions, same-device layout or capacity monitoring. Validate these on an isolated equivalent filesystem before approved production provisioning.

Reads enforce hash/length/size/key rules and use one verified buffer; POSIX O_NOFOLLOW protects the final file, but ancestor/root directories must also be trusted against symlink replacement. Legacy reads retain their migrated relative key. Only recognized aged temp/probe files are swept; final or unreferenced content-addressed artifacts are not garbage-collected. Capacity planning must include orphans, legacy PDF/HTML and backup copies. Record free bytes/inodes, growth, snapshot age, mount identity/permissions and a restore drill; set owner-approved alerts. Windows local tests skip directory fsync and one symlink test and are not production durability evidence.
