| Runtime grants | `select, insert, update` (no delete) | yes |
| Retry deadline | none | derivable from `requested_at` + configuration |
| Terminal immutability at DB level | **no guard trigger** (unlike `issuance_operations_guard`) | enforceable in the application via conditional, fenced updates |
| Failure message text | **none** (deliberately) | correct: provider text must not be persisted |

**Does R1.6 require migration `000010`? NO.** Every R1.6 invariant can be
implemented on the current schema:

- one delivery per key → binding pk;
- at most one sender per attempt → `generation` + lease;
- terminal states are never left → `where status = 'sending' and generation = :g` updates;
- `unknown` for expired `sending` → sweep fenced by a generation bump;
- retry timing → `next_attempt_at`;
- pinned bytes → `document_sha256`;
- no PII in failures → code only.

Optional and not required: a `quote_deliveries_guard` trigger. It would reject
leaving `sent`/`failed`/`unknown`, reject a generation decrease, and reject
changes to recipient or `document_sha256`. That would give the DB-level parity
the other V2 tables have, and it would be migration `000010`. This is decision
**W1**. Default: **no migration**.

## 4. Delivery state machine (frozen)

Sources: Domain §10, Idempotency §5, State machine §1/T8, Migration §1.3,
OpenAPI `Delivery`.

```
POST …/deliveries/email (one tx: binding + row + audit quote.delivery.requested)
        │
        ▼
     pending ──claim (gen+1, lease)──► sending ──provider accepted──────► sent       (terminal)
        ▲                                │  ├─known NOT accepted, retryable─► pending (next_attempt_at)
        │                                │  ├─known NOT accepted, permanent / exhausted ─► failed (terminal)
        └────────────────────────────────┘  └─ambiguous (timeout after send, crash, lease expired) ─► unknown (terminal)
     pending ──quote cancelled (T8)──► failed (quote_cancelled)
```

| Question | Frozen answer |
|---|---|
| When is a row created? | Only by `POST /v2/quotes/{id}/deliveries/email`, in one transaction with the binding, the recipient snapshot, the pinned `documentSha256` and the audit event (Domain §10.2). Issuance never creates one (D-3, §10.1) |
| When is it eligible? | `pending` with `next_attempt_at ≤ now`. The first `next_attempt_at` is `requested_at` |
| Retry | "Only failures known not to have been accepted are retried" (§10.2). The row goes back to `pending` with backoff. The schedule and limit are **not frozen** (implementation parameters, §14) |
| Ambiguous outcome | `unknown`, "NOT blindly retried" and "not retried automatically" (§10.2, Idempotency §5). A new key is a deliberate new delivery |
| Terminal | `sent`, `failed`, `unknown`. There is no operator transition out of any of them |
| Cancellation | T8: deliveries **not yet `sending`** become `failed` (`quote_cancelled`). A `sending` row finishes its attempt |
| Relation to the quote | Delivery outcome never changes the quote state or the document (§10.2). The `quotes_guard` trigger has no path from delivery to quote anyway |
| Can delivery failure affect the quote? | **Never.** delivery failure ≠ issuance failure (separate tables, separate lifecycle, separate workflow) |

Not frozen, and recommended for R1.6 (needs owner confirmation, **W2**): the
quote becomes **expired** while a delivery is `pending`. The contract only
states the request-time rule (`issued` only) and T9 has no side effect. The
recommendation is that the worker re-checks the effective quote status at
claim time and fails a delivery whose quote is no longer `issued`
(`quote_expired` / `quote_cancelled`). It must not send an offer that has
already expired. This is consistent with `409` at request time and does not
change the quote.

Gap in the existing T8 implementation (R1.6A, small): cancel fails the
pending deliveries but appends no `quote.delivery.failed` audit event per
delivery. Domain §11 lists delivery events, so each one should be recorded
with `data.deliveryId` and `data.errorCode = quote_cancelled`.

## 5. Email trigger

- **Issuance never creates or sends a delivery** (D-3, §10.1, OpenAPI
  create/issue descriptions, validator check "Email cannot happen during
  issuance"). R1.6 preserves "Quote issued → zero automatic deliveries".
- The only trigger is `POST /v2/quotes/{quoteId}/deliveries/email`, with
  `Idempotency-Key`, optional `X-Correlation-Id`, and body
  `EmailDeliveryRequest {recipient?: {email, name?}}` (closed schema).
- Provider **disabled** (the default and the initial production
  configuration): `503 dependency_unavailable`,
  `details.dependency = "email_provider"`, **nothing queued, nothing bound**
  (§10.1).
- Provider enabled but unhealthy (for example a Gmail outage): the request
  still queues `202`. Queueing needs only persistence. The outage only
  affects the worker. The contract ties `503` to "disabled", not to provider
  health.
- Response `202` with `Delivery`, `Location:
  /v2/quotes/{quoteId}/deliveries/{deliveryId}`. A replay returns `202` with
  `Idempotent-Replay: true` and the delivery's **current** state.

Recommended evaluation order, from Domain §12:

`413/400` → `401` → `403 (quotes:delivery:email)` → binding lookup (replay /
`409 idempotency_key_conflict`) → provider-enabled check (`503
email_provider`) → `404 quote_not_found` (visibility) → `422
delivery_recipient_missing` → `409 invalid_state_transition` → accept.

Placing the provider check after the binding lookup keeps I-4. A key bound
while the provider was enabled still replays after it is disabled. This
placement is decision **W3**; it is the default.

The contract orders `422` before `409`. A draft with no email therefore
answers `422 delivery_recipient_missing`, not `409`. That is acceptable and
it is the frozen order.

## 6. Delivery authorization (frozen; A4 not extended)

`quotes:delivery:email` is the endpoint scope. Visibility (created by *P*, or
*P* holds `quotes:read:any`) is required. **Creator-only does not apply.**
A4 enumerates draft edit, issue and cancel exhaustively. Security §2 grants
delivery for "a visible issued quote", and the "Customer communication"
profile (`quotes:read`, `quotes:read:any`, `quotes:delivery:email`) exists
precisely for cross-principal sending.

| Caller | Result |
|---|---|
| Own quote + `quotes:delivery:email` | allowed (`202` if `issued`) |
| Foreign quote + `quotes:read:any` + `quotes:delivery:email` | **allowed** (`202` if `issued`) |
| Foreign quote + `quotes:delivery:email`, no `quotes:read:any` | `404 quote_not_found` (existence hiding) |
| `quotes:read:any` without `quotes:delivery:email` | `403 forbidden` (`requiredScope = quotes:delivery:email`), before any binding lookup |
| `principalType` (`operator`/`service`) alone | grants nothing (`403` without the scope) |
| Unknown quote | `404 quote_not_found` |

`GET /v2/quotes/{id}/deliveries/{deliveryId}` requires `quotes:read` plus
visibility of the quote. An unknown delivery, a non-visible quote, or a
delivery that belongs to another quote answers `404 delivery_not_found`
(`quote_not_found` for a non-visible quote, matching the existing reads).
Bindings stay principal-scoped. A principal never replays or conflicts with
another principal's delivery key.

## 7. Quote states eligible for email

From state machine §4 and OpenAPI `requestEmailDelivery`. The effective
(projected) status is used.

| Quote state | Result |
|---|---|
| `draft` | `409 invalid_state_transition` (`details.status = draft`) |
| `issuing` (any operation state, including `failed`) | `409 invalid_state_transition` |
| `issued` (effective, `now < validUntilExclusive`) | **`202`** |
| `expired` (projected or materialized) | `409 invalid_state_transition` (`details.status = expired`). **No historical resend** |
| `cancelled` after issue | `409 invalid_state_transition`. **No resend** |
| `cancelled` before issue / after failed issuance | `409 invalid_state_transition` |

A formal email therefore always has a committed manifest. Only `issued`
qualifies, and `issued ⇒ manifest` is enforced by the deferred trigger
`quotes_require_document`. The document **stays downloadable** for expired
quotes and for quotes cancelled after issue (`GET /document 200`), but it is
not emailable.

## 8. Document source for email

- Source of truth: the committed `quote_documents` manifest. The request
  transaction copies `pdf_sha256` into `quote_deliveries.document_sha256`
  (pinned).
- Worker path: load the manifest, then call `readVerified(manifest)` (R1.5B4,
  the same verifier as `GET /document`), which returns a **Buffer** of
  verified bytes. Assert `sha256(bytes) == document_sha256`, then attach.
- Port compatibility: `EmailSenderPort.attachments[].content: Buffer`. The
  Gmail MIME builder base64-encodes the Buffer. No filesystem path crosses
  the port.
- Filename: reuse the existing sanitized `documentFileName(quoteNumber)` from
  the document route. It is built from the number only.
- **No re-rendering and no email-specific PDF.** A verification failure at
  send time (missing or corrupt artifact) is known to be "not sent". It is
  retryable within the retry window. It then ends as `failed`
  (`document_storage_failed`), and the same `document.integrity_failed`
  operator log is emitted.

contract makes the PDF the formal artifact (§5 success evidence, §9). The
email carries no formal fields of its own.

Safe fields to include:

- `quoteNumber` (opaque business identifier);
- the issue date as the Chile civil date of `issuedAt`;
- optionally the validity-through date, copied verbatim from
  `validity.validThroughLocalDate` with the frozen wording;
- the brand display name;
- recipient greeting from `recipient.name` when given, otherwise a generic
  greeting;
- the statement that the formal quote is the attached PDF;
- a contact line from deployment configuration (`QUOTE_EMAIL_REPLY_TO`).

Must not include:

- lines, quantities, unit amounts, totals or tax amounts;
- tax statements (U2);
- issuer legal name, RUT or address (U3);
- shipping;
- customer RUT, phone or address;
- `externalCorrelation`, internal ids beyond `quoteNumber`, or provenance.

With that content the email depends on **neither U2 nor U3**. The Spanish
copy (subject, greeting, closing) still needs owner content approval before
production. That approval is an R1.7 gate, not an R1.6 blocker.

## 12. Exactly-once vs at-least-once

Gmail `users.messages.send` has no idempotency key. No repository code
performs provider-side lookup.

| Window | What happens | Durable state | Outcome |
|---|---|---|---|
| A. `sending` → provider accepts → process dies before DB records `sent` | Email delivered | row `sending`, lease expires | sweep → **`unknown`** (email exists; the status is not `sent`) |
| B. Provider call times out or resets after the request was written | Email may or may not exist | worker classifies the outcome as ambiguous | **`unknown`** |
| C. Provider success → `sent` commit outcome unknown (connection lost) | Email delivered | row still `sending` (rolled back) or `sent` | if `sending`: lease expiry → `unknown`; otherwise `sent` |
| D. Connect refused / DNS / token refresh failure / HTTP 429 / 4xx validation | Not accepted | known | retry (`pending`) or `failed` |

The truthful guarantee:

- **Command:** exactly one delivery record per `(principal,
  quote.delivery.email, key)`. This is I-1 and is proven by the binding pk.
- **Side effect:** **at most one automatic provider acceptance per
  delivery.** The system never re-sends a delivery whose previous attempt
  could have been accepted. `sent` is definitive. `failed` is definitive
  "not sent", provided the classification is correct. `unknown` means 0 or 1
  emails.
- **Not exactly-once, not at-least-once.** The system can under-report
  (`unknown` while delivered). It can also deliver zero emails for a request
  if the outcome was ambiguous and nobody re-requests.
- **Duplicates are only caller-initiated**: a new key after `unknown` or
  `failed`.

Reconciliation possibilities:

- A deterministic `Message-ID: <delivery.{deliveryId}@{sender-domain}>`
  header makes a later search by `rfc822msgid:` possible. An operator can run
  it in the Gmail UI of the sending mailbox. The API needs
  `gmail.readonly`/`gmail.metadata` scope, which is unknown.
- **Unverified:** whether Gmail preserves a caller-supplied `Message-ID` on
  `messages.send`. It must be verified against a **non-production** mailbox
  under a separate owner authorization (R1.6B optional gate) before it is
  documented as a reconciliation tool.
- Automatic reconciliation (resolving `unknown` from a provider search) is
  **not in the contract**, because `unknown` is terminal. It is FUTURE and
  needs an amendment.

## 13. Delivery idempotency

- Binding `quote.delivery.email` → `delivery_id`. Same rules as quote
  bindings (Idempotency §3, §5). Scope `(principal, operation,
  SHA-256(key))`. Fingerprint = JCS of `{operation, pathParameters:
  {quoteId}, body}`.
- The same key and the same body return **the same delivery** in its current
  state (`202`, `Idempotent-Replay: true`, audit `idempotency.replayed`).
  They **never** cause another provider call and never change the row.
- The same key with a different body (for example another recipient) answers
  `409 idempotency_key_conflict`.
- A rejected request (`4xx`, `503` including provider-disabled) binds
  nothing.
- **Command idempotency ≠ side-effect exactly-once.** The key guarantees one
  delivery record. §12 bounds what that record can do externally. A replay
  of a delivery that ended `unknown` returns `unknown`. It never resends.
- Lookup already works: `GET /v2/idempotency/current?operation=quote.delivery.email`.

## 14. Retry policy

| Aspect | V1 (`retry-policy.ts`) | R1.6 requirement |
|---|---|---|
| Schedule | 1 m, 5 m, 15 m, 1 h, 4 h, then capped (`maxAttempts` parameter) | Not frozen. Recommended: same shape, as configuration (`QUOTE_EMAIL_RETRY_*`) |
| Limit | `maxAttempts` | `maxAttempts` (default 6) **or** deadline `requested_at + window` (default 24 h). At the limit: `failed` with the last error code. Needs no column |
| Transient (retry) | 429, 5xx, timeouts, any network `TypeError` | **Only failures known not to be accepted**: token-phase failures; connect-phase errors (`ECONNREFUSED`, `ENOTFOUND`, `EAI_AGAIN`, TLS handshake before request); send HTTP 429; document read failure; provider not configured at run time |
| Permanent (`failed` at once) | 400/422, `invalid_grant`, 401/403, unexpected | send HTTP 400/413 (`provider_rejected_message`); invalid recipient; quote no longer `issued` (W2) |

## 15. Delivery worker

The contract fixes it: "The outbox worker uses the same lease/generation
pattern" (Idempotency §5). The schema has the columns. The **mechanics differ
from issuance on one point.** Issuance reclaims an expired lease and re-runs,
because rendering is idempotent. **A delivery must never be reclaimed for
re-sending.** An expired `sending` lease means a provider call may have
happened.

Minimum mechanism, with no lease renewal and no failpoint framework copied:

```
claim (tx, FOR UPDATE SKIP LOCKED, batch ≤ N):
  UPDATE d SET status='sending', generation=generation+1, lease_owner=:me,
               lease_expires_at=now()+leaseMs, attempt_count=attempt_count+1,
               last_attempt_at=now(), updated_at=now()
  WHERE status='pending' AND next_attempt_at<=now()  → :g
  + same tx: re-check effective quote status = issued, else
    status='failed' (quote_expired / quote_cancelled), audit, no send (W2)
send (outside tx): readVerified(manifest) → assert sha == document_sha256
                   → mail port with timeouts sum < leaseMs
                   → log provider acceptance (deliveryId, providerMessageId) BEFORE commit
complete (tx, fenced: WHERE delivery_id=:id AND generation=:g AND status='sending'):
  accepted     → sent, sent_at, provider_message_id, lease cleared; audit quote.delivery.sent
  retryable    → pending, next_attempt_at=backoff, last_error_code; (no audit, or attempt event in data)
  permanent    → failed, last_error_code; audit quote.delivery.failed
  ambiguous    → unknown, last_error_code; audit quote.delivery.unknown; operator log
  0 rows       → fenced out: log `delivery.late_result` with deliveryId/providerMessageId; nothing else
sweep (persistence-gated):
  UPDATE d SET status='unknown', generation=generation+1, lease cleared,
               last_error_code='delivery_outcome_unknown'
  WHERE status='sending' AND lease_expires_at<now(); audit quote.delivery.unknown
```

- Lease duration is configuration, default 120 s. It must exceed token
  timeout + send timeout + margin (for example 10 s + 30 s). That bound makes
  renewal unnecessary.
- Gate: the send runner requires the `DELIVERY_SEND` capability (§21). The
  `unknown` sweep requires `PERSISTENCE` only.
- Shutdown: stop claiming. An in-flight provider call finishes or times out
  within the lease. An unfinished row becomes `unknown` by sweep (never
  re-sent).
- Known false-`unknown` window: a crash between claim and the provider call.
  It is harmless (no duplicate), it is documented, and it can be reduced
  later without a schema change.
- A single process with a single slot is enough at current volume.
  Concurrency comes from `SKIP LOCKED` across instances.
- The `BackgroundJobManager` slot `emailDelivery` exists. The runner status
  stays in-memory observability only.

## 16. Duplicate email risk

Scenario: worker A sends, the provider accepts, A loses its DB connection,
and worker B "retries".

- **B cannot re-send that delivery.** The row is `sending` under A's
  generation. B's claim selects only `pending`. When A's lease expires, the
  sweep moves the row to `unknown` (terminal) and bumps the generation. A's
  late completion matches 0 rows. **Duplicate count from the system: 0.**
- This contrasts with V1. The deleted V1 worker reclaimed stale
  `processing` outbox rows (`locked_at <= now - leaseMs`) and **sent again**.
  It must not be salvaged.

| Duplicate source | Preventable? | Mitigation |
|---|---|---|
| Replay of the same key | yes | binding replay (no send) |
| Concurrent workers | yes | `SKIP LOCKED` claim + generation |
| Lease expiry during or after the provider call | yes | expired `sending` → `unknown`, never re-claimed |
| Retry after a misclassified "not accepted" error | yes, by classification | send-phase 5xx and resets are `unknown` (W4) |
| Caller sends a new key after `unknown` | **no (deliberate)** | contract: "A new key is a deliberate new delivery". Document for consumers. Deterministic `Message-ID` lets recipients' MUAs and operators spot duplicates |
| Provider-side duplicate on its own retries | outside control | — |

Fundamentally ambiguous: the existence of the email in windows A/B/C of §12.
The system reports these honestly as `unknown`.

## 17. Operator retry (T10)

The primitive exists: `PostgresIssuanceOperationRepository.createOperatorRetry({quoteId,
failedOperationId, actorPrincipalId})`. It takes the quote lock, requires the
quote to be `issuing` with a current operation that is `failed`, re-verifies
the snapshot hash, inserts an `operator_retry` operation with a new
deadline, bumps the version and appends `quote.issue.accepted` with
`retryOf`. It serializes against T11.

What is missing: any way to invoke it, and any way to find failed operations
other than logs (`issuance.deadline_failed`, the A5 non-retryable failure
log) and per-quote reads.

Surface decision: **CLI only.** The state machine defines T10 as "operator
procedure (**no public endpoint**)". An HTTP endpoint would need a contract
amendment plus a new scope. It would also contradict "V2 defines no
cross-principal mutation scope" (A4).

| Item | Recommendation |
|---|---|
| Commands | `npm run issuance:retry[:runtime] -- --quote <uuid> --operation <failedOperationId> --operator <principalId> --reason <code> [--yes]` and read-only `npm run issuance:failed[:runtime]` (lists quotes whose current operation is `failed`: `quoteId`, `quoteNumber`, `operationId`, `lastErrorCode`, `attemptCount`, `completedAt`). JSON output, no PII |
| Authority | Operator plane: host access + database credentials, the same as `documents:verify` and migrations. No bearer token |
| Principal | `--operator` is recorded as `actorPrincipalId`. It must match the principal code pattern and must not be `system` or `legacy-v1`. Whether it must also exist in the principal registry with `principalType = operator` is decision **W6** (recommended: yes) |
| Reason / note | `reasonCode` (`^[a-z][a-z0-9_]{1,63}$`) added to the audit `data`. No free-text note in audit (PII rule). This is a minimal extension of the audit payload, not of the state logic |
| Idempotency | Natural, through `failedOperationId`. A second run gets `INVALID_STATE` with the current operation id, which the CLI reports as "already retried / not applicable". No idempotency key |
| Exit codes | `0` retry created, `3` not applicable (`INVALID_STATE` / `QUOTE_NOT_FOUND`), `2` snapshot integrity error, `1` could not run |
| Response | `{quoteId, failedOperationId, newOperationId, deadlineAt}` |
| Audit | the existing `quote.issue.accepted` (`data.retryOf`, `data.reasonCode`) under the operator's principal id |
| Visibility | full (operator plane). Nothing is exposed over HTTP |
| Safety | refuses if the schema head is not the expected head. Prints a dry-run summary unless `--yes` |

The T10 state logic is not re-implemented.

## 21. Readiness granularity

Today the single `businessGate()` checks lifecycle → database → schema →
artifact storage → renderer, in that order, for **every** business route. A
renderer outage therefore returns `503` on reads, lists, operation reads,
audit, idempotency lookup, cancel, drafts and `GET /document`.

Proposed capability model. It lives inside `DependencyMonitor`, and its
inputs are the existing cached records:

| Capability | Requires | Routes / jobs |
|---|---|---|
| `PERSISTENCE` | not shutting down + database `up` + schema `READY` | `GET /v2/quotes`, `GET /v2/quotes/{id}`, `GET /v2/operations/{id}`, `GET …/audit`, `GET /v2/idempotency/current`, `POST/PATCH drafts`, `POST …/cancel`, `GET …/deliveries/{id}`, deadline sweep, delivery `unknown` sweep, expiry materialization |
| `DOCUMENT_READ` | `PERSISTENCE` + artifact storage `up` | `GET …/document`, integrity job |
| `ISSUANCE` | `PERSISTENCE` + storage + renderer | `POST /v2/quotes`, `POST …/issue` (acceptance stays fully gated: the inline attempt needs both), issuance worker |
| `DELIVERY_REQUEST` | `PERSISTENCE` (+ provider **configured**, otherwise `503 email_provider`) | `POST …/deliveries/email` |
| `DELIVERY_SEND` | `DOCUMENT_READ` + provider configured | delivery send runner |
| `DEADLINE_SWEEP` | `PERSISTENCE` (= today's `isPersistenceReady`) | issuance deadline sweep |

`DependencyMonitor` can expose this cleanly as `gate(capability):
BusinessGateRejection | null`. `businessGate()` stays as `gate("ISSUANCE")`
for compatibility. The readiness gate hook then reads a per-route
`config.capability`, set the same way as `config.requiredScope`, so a route
without one fails at startup. `readiness()` (the `/health/ready` body) does
**not** change.

Contract compatibility: Domain §12 says `503` "can occur at any step that
needs a dependency". §13 requires `503` on a database outage, which still
holds because every capability includes `PERSISTENCE`. No contract change is
needed.

Refinement, optional and not required: the storage probe fails on
not-writable (`storage_full`, `storage_read_only`). A read-only document
volume would still block `DOCUMENT_READ`. Splitting the read and write
outcomes is possible because the failure category is already recorded. It
is noted, not recommended for R1.6.

Tests that assert "business routes `503` on renderer failure" (R1.3/R1.5
health and reliability suites) must be updated to the capability matrix.
That is an intended behavior change, documented in the R1.6D notes.

## 22. Health semantics

`/health/ready` is frozen (Domain §13 and OpenAPI `Readiness.checks` closed
to `database, schema, artifactStorage, renderer, lifecycle`). It means "this
instance can perform its full write path (issuance)". It never includes
email: the closed schema has no slot for it, and `health-route.ts` already
states "email never affects readiness".

Recommendation: keep `/health/ready` exactly as is. Introduce capability
readiness **internally** for route gating and job gating only. Capabilities
are not exposed as a new endpoint, because `DependencyHealth` is closed and
exposing them would need a 2.x amendment. With that design a Gmail outage
affects only the delivery send runner and `emailProvider` status. It never
affects readiness, quote reads or document reads. A renderer outage no
longer blocks reads or document downloads.

## 25. Integrity job / command

- Exists: `documents:verify` (detection only, keyset batches of 200, exit
  codes 0/2/1, no PII).
- Expected:
  - Domain §9.4: "A periodic integrity check verifies every manifest's file
    hash".
  - Roadmap R1.6: "Artifact integrity check job; operator repair procedure
    (hash-reproducing re-render only)".
  - Exit criterion: "integrity job tests".
- Justification for periodic: the contract requires it. It should not be
  always-on at high frequency. Recommended:
  - an in-process runner, opt-in by configuration (`QUOTE_INTEGRITY_CHECK_INTERVAL_MS`,
    default disabled in development, daily in production, set in R1.7);
  - full scan via the existing verifier, rate-limited by batch;
  - gated on `DOCUMENT_READ`;
  - emits `document.integrity_failed` per problem plus a summary log;
  - never affects readiness, never repairs.
- Alternative: an external scheduler running `documents:verify:runtime`. That
  is deployment-only (R1.7) and has no R1.6 test surface. This choice is
  decision **W7**.
- Repair command (`documents:repair`): re-render from the frozen snapshot
  **only if** the manifest's `rendererVersion` and `templateVersion` equal
  the running build. Publish through the write-once content-addressed store
  **only if** `sha256 == manifest.pdfSha256`. Never touch the manifest.
  Migrated V1 manifests are not repairable (V1 renderer retired) and are
  reported as such. **R1.6C.**
- Operational alert integration (paging) is R1.7 deployment.

## 31. Recommended R1.6 slices

The proposed A/B/C/D shape holds. The boundaries below are adjusted to the
evidence. Each slice requires explicit authorization.

### R1.6A — Delivery request core (no provider execution)

- Composition: a `MailSenderPort | null` decided by configuration
  (`QUOTE_EMAIL_PROVIDER`), or by a `BuildApplicationOverrides.mailSender`
  test seam. In R1.6A no worker exists. With the default `disabled`
  configuration, production behavior is `503 email_provider`.
- `POST /v2/quotes/{id}/deliveries/email`:
  - closed schema with a strict `recipient.email`;
  - evaluation order per §5;
  - authorization per §6;
  - eligibility per §7;
  - recipient resolution (`recipient.email` → `customer.email` → `422`);
  - masked recipient;
  - pinned `document_sha256` from the committed manifest;
  - one transaction: delivery row (`pending`, `next_attempt_at = now`,
    `origin = v2`), binding and audit `quote.delivery.requested`
    (`data: {deliveryId, documentSha256}`, no PII);
  - `202` + `Location`; replay `202` + `Idempotent-Replay`; conflict `409`.
- `GET /v2/quotes/{id}/deliveries/{deliveryId}` per §19.
- T8 gap: append `quote.delivery.failed` (`quote_cancelled`) per failed
  pending delivery.
- Gate: `DELIVERY_REQUEST` if R1.6D's capability gate has landed, otherwise
  the existing gate (interim).
- Tests:
  - OpenAPI conformance for request, response and every error;
  - the authorization matrix (§6, all five rows);
  - the state matrix (§7, every state including projected expiry);
  - replay, conflict and cross-principal key independence;
  - concurrent same key ×N gives one delivery;
  - provider disabled gives `503` with nothing bound and no row;
  - a bound key still replays after the provider is disabled (W3);
  - no email or provider call anywhere (fake port asserts zero calls);
  - issuance still creates zero deliveries;
  - cancel fails pending deliveries and records audit;
  - recipient injection payloads rejected `422 validation_error`.
- No migration. No change to issuance.

### R1.6B — Delivery execution (worker, envelope, Gmail)

- Generic mail port with the outcome model. Fake sender (tests only, through
  overrides).
- Gmail adapter refactor (§11).
- V2 envelope view model and template (§9–§10), built from the issued
  snapshot loader. No V1 types.
- Attachment = `readVerified` bytes with a hash assertion.
- Delivery worker: claim, complete and the `unknown` sweep (§15).
- Retry policy configuration and classification (§14).
- `emailDelivery` runner + `emailProvider` status + `emailDelivery` queue
  metrics.
- Audit `quote.delivery.sent|failed|unknown`.
- Log events `delivery.sent`, `delivery.attempt_failed`,
  `delivery.outcome_unknown` and `delivery.late_result` (no PII).
- Narrow `test-seams` §33.
- Delete the V1 email/domain remnants (§29) once nothing imports them.
- Tests:
  - accepted → `sent` once;
  - retryable not-accepted → `pending` with backoff, then `sent`;
  - permanent → `failed`;
  - exhaustion → `failed`;
  - ambiguous (timeout after write, reset, 5xx per W4) → `unknown`, never
    retried;
  - crash after provider accept (process kill) → `unknown`, provider called
    exactly once;
  - zombie completion after sweep → 0 rows, no state change;
  - two workers → one claim;
  - cancel during `pending` → never sent; cancel during `sending` → attempt
    completes;
  - quote expired before claim → `failed` (W2);
  - document missing → retry then `failed` `document_storage_failed`, no
    send;
  - attachment bytes equal the committed PDF (hash);
  - MIME: single recipient, encoded headers, deterministic `Message-ID`,
    no PII in logs (redaction tests);
  - Gmail outage → reads and document unaffected, readiness unaffected.
- Optional gate, separately authorized: one live send to a non-production
  mailbox to verify `Message-ID` preservation and the attachment hash. It is
  not required to close R1.6B.

### R1.6C — Operator controls

- `issuance:retry` and `issuance:failed` CLIs (§17).
- `documents:repair` CLI (hash-reproducing only, §25).
- Runtime variants in `dist/scripts`.
- Tests:
  - T10 via CLI on a T6- and a T12-failed operation leads to issued;
  - a second run is "not applicable";
  - T10 racing T11 (both orders);
  - snapshot-integrity refusal;
  - repair restores byte-exact bytes and refuses on hash mismatch or a
    legacy V1 manifest;
  - no HTTP route exists for either.

### R1.6D — Capability readiness, jobs, hardening, retirement tooling

- Capability gate (§21), so document GET and reads become independent of the
  renderer. `/health/ready` is unchanged.
- Expiry materialization runner (§24).
- Integrity job (W7).
- Real queue metrics for issuance and expiry.
- `/v1/*` catch-all → `410 api_version_retired` (code only; live at R1.7

- Log redaction tests (bodies, `Authorization`, raw keys, recipient,

## 32. Exit criteria

### R1.6A

1. `POST …/deliveries/email` and `GET …/deliveries/{id}` conform to OpenAPI
   (every example and every response validates).
2. No automatic email: issuance creates zero delivery rows (existing
   assertions stay green), and the fake port records zero calls in A.
3. The authorization matrix in §6 passes exactly: allowed / `403` / `404`.
   A4 is unchanged.
4. Command idempotency: same key → same delivery (×N concurrent); different
   body → `409`; `4xx`/`503` bind nothing.
5. Only effective `issued` quotes queue; the others answer `409` per §7.
6. Provider disabled: `503 email_provider`, nothing queued.
7. A delivery never changes quote state, version or document (DB assertion).
8. T8 audit events present.

### R1.6B

1. The pinned, verified committed PDF is the only attachment (hash equality).
2. Ambiguous outcomes become `unknown` and are never retried automatically.
   An expired `sending` lease goes to `unknown`.
3. Retries are durable: `next_attempt_at` and `attempt_count` survive a
   restart. Permanent failures and exhaustion stop at `failed`.
4. Crash after provider acceptance: provider called exactly once, final
   state `unknown` or `sent`, never a second call.
5. No V1 email commercial authority remains: the V1 view model, template
   content, signature, unit-price derivation and IVA note are deleted.
6. A Gmail outage does not affect `/health/ready`, quote reads or document
   reads.
7. Redaction tests: no recipient, name, body, provider text or token in logs
   or audit.

### R1.6C

1. An operator can trigger T10 safely: CLI only, audited with the operator id
   and reason, idempotent by precondition, and races with T11 serialized.
2. Repair never writes non-matching bytes.

### R1.6D

1. Capability readiness is granular. A renderer outage leaves reads and
   document GET at `200`. Storage down leaves document GET `503` and reads at
   `200`. A database outage leaves everything `503` with liveness `200`.
   `/health/ready` is byte-identical in shape and rules.
2. Expiry materialization is idempotent, writes `quote.expired` with
   `expiredAt = validUntilExclusive`, and is persistence-gated.
3. The integrity job detects missing or corrupt artifacts and never repairs
   or blocks readiness.
4. `/v1/*` → `410`.
5. Real queue metrics are reported.
6. All regression and crash suites stay green: `npm verify`, validator
   464/464, fresh Docker E2E, crash matrix.
7. No migration `000010`, unless W1 is approved.
8. U2/U3 stay explicitly R1.7 if unresolved.
9. The migration rehearsal report (synthetic) is committed.
